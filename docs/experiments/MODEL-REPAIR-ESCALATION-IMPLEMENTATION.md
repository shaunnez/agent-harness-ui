# Candidate Repair escalation implementation

The routing slice in `MODEL-REPAIR-ESCALATION-PLAN.md` is implemented on this branch. A new task snapshots an explicit optional Repair rung per workflow profile. Saved settings that predate this field migrate to **Off**, and changing settings does not rewrite a task. The Frontier settings page shows the selected Repair policy, stronger policy and candidate repair limit together; New Task shows the resulting rule. A task-level Repair override pins the role and disables automatic escalation.

Only an exact, durable authorizing REPAIR gate with a fresh `repair_required` reason and an explicitly bound blocking P0/P1 `candidate-defect` can trigger the rung. A Test failure without such a structured finding can still use ordinary Repair, but does not upshift its model. P2 wording, verification gaps, stale or wrong candidates, infrastructure failures and cancelled runs do not trigger an upshift. Reservation, spawned agent, retained run, Run activity and evaluation export carry the selected/effective policy and authorizing gate. Escalation does not add a repair attempt. Package retries and planning uncertainty remain outside this slice.

Deterministic tests exercise the decision table, settings round trip, task snapshot, provider boundaries, the real fake-runtime Repair flow and retained provenance. The fixture Frontier page was inspected at `?mode=fixture#settings`, including the Off → Sol XHigh control. This verifies routing and presentation; it does **not** measure whether a stronger model repairs better.

The earlier full-delivery evaluations did not isolate candidate Repair. The bounded live smoke below verifies dispatch; the paired replay and its promotion decision are recorded in `MODEL-REPAIR-ESCALATION-REPLAY.md`. Standard/high-risk Codex defaults remain Off. H03 remains held out.

## Bounded live Repair smoke (23 September 2026)

One disposable, local Git repository exercised the branch's actual candidate Repair path with one real Codex provider call. Earlier stages and the Dev Review judgment were deterministic setup, not real model runs. The repository's declared package smoke test passed on candidate `C1` revision 1 (`97374e1bab2e70e134a49c32a92ed093c801cfba`), while an independent acceptance check for trimming **and** case-insensitive comparison failed. A separately held reference implementation passed that same check; its patch was not in the agent's worktree. The retained Dev Review gate bound an explicit blocking P1 `candidate-defect` to that exact candidate (`2850bca5-2ed4-46ce-a652-5d2ae49120c0`, artifact `73ccf447-d59e-45f7-a929-cd2c32f7a5ac`), and freshness was `repair_required`.

The Repair reservation selected `gpt-6-sol` High and escalated to `gpt-6-sol` XHigh, citing that gate in the reservation, run and Run activity. The actual provider invocation used XHigh. It completed in 49 seconds, with 116,276 input tokens (106,624 cached) and 1,389 output tokens; the harness reported a $0.054519 **API-rate estimate**, not an attributable ChatGPT-plan charge. It committed exactly one new candidate revision, `C1` revision 2 (`dcb9ebd35853bac1cd16a495dd3100e8a76bfdc7`), changing the comparator to trim and fold case. The committed worktree was clean, the independent acceptance check passed, the retained Repair run completed, and the task returned to `ready-for-review`. The previous Dev Review gate was correctly stale with `revision_change`; Test and Final Review had not run. The existing Implement attempt count moved from 1 to 2; escalation did not grant an extra attempt. The owner-only local receipt is `/var/folders/nr/bpphtrj50gz4_rjqtsdm36_00000gp/T/repair-escalation-pr130-h4T2me/result.json`.

This smoke proves provider dispatch, provenance, revision lineage and one behavior correction for the enabled rung. It does not show that XHigh beats High or prove the full workflow through re-review and Test. The paired comparison and its limits are in `MODEL-REPAIR-ESCALATION-REPLAY.md`.
