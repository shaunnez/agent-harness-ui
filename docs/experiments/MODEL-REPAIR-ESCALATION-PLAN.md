# Focused model escalation plan

**Status:** plan only. Implement after the provisional model defaults in PR #129 have landed; do not run H03 or start another full delivery campaign as part of this work.

## Outcome and boundary

When a candidate has a verified, material code defect, its next permitted Repair run can use one stronger, same-provider policy. The decision must be predictable, bounded by the existing repair allowance, visible in Frontier, and measurable against a repair that stayed on the selected policy. This first slice covers **candidate Repair** only. Planning uncertainty and failed package qualification need different evidence and reservation handling; they are follow-ups, not additional triggers hidden in this slice.

## Current behavior to preserve or correct

- `server/effective-policy.mjs` resolves selected versus effective policy before reservation. Only an unpinned `repair` role can upshift, following a candidate-bound `REPAIR` gate with a blocking `candidate-defect`. The policy and reason are retained on the reservation and run. Provider constraints and role pins must keep working.
- `server/task-policy-snapshot.mjs` currently manufactures the stronger Repair policy from that provider's **Plan** default. This is implicit and can be an equal policy: under PR #129, standard/high-risk Codex Repair is already Sol High and has no upshift. Fast Codex can move Luna High to Sol High; all-Claude can move Sonnet 5 High to Opus 5.5 High.
- The current trigger also searches finding prose for architectural keywords. A P2 finding can therefore spend a stronger model because of wording rather than a structured severity decision. Package retries execute under the `implement` role inside one implementation reservation, so changing their model mid-attempt requires a separate design.
- Existing package and candidate repair limits, candidate revision lineage, and fresh gate requirements remain authoritative. An upshift never grants an extra attempt or turns a baseline/environment failure into a candidate defect.

## Implementation slices

1. **Lock down the decision contract.** Use the retained gate's exact candidate ID/revision and a validated, blocking `candidate-defect`. Automatically upshift for P0/P1 only; a P2 criterion breach can still receive ordinary Repair but does not upshift. Verification gaps, baseline failures, timeouts, cancelled runs, stale gates, invalid plans, and unpinned prose alone cannot trigger it. Preserve explicit task role pins and provider-only choices. Permit at most one configured stronger rung for a Repair run, never a cross-provider substitution. Add a decision-table test before editing behavior.
2. **Make the rung explicit.** Replace the Plan-role inference with a named, optional Repair escalation policy per workflow profile in saved Settings, snapshotted on new tasks. Frontier Settings shows the selected Repair policy, the stronger policy or **Off**, and the existing repair-attempt limits together; New Task's Agent setup shows the resulting effective rule. Validate the model, reasoning level, allowlist, provider and task pin at snapshot/reservation. Existing task snapshots remain unchanged; existing saved settings must not silently acquire a more expensive rung. Presets may offer Fast Codex Luna High → Sol High and all-Claude Sonnet High → Opus High, but standard/high-risk Codex stays **Off** until a stronger rung earns promotion. A manual Repair override remains a pin and disables automatic upshift for that task.
3. **Prove the actual execution path without a provider call.** In `tests/effective-policy.test.mjs` and `tests/orchestrator-runtime-policy.test.mjs`, cover eligible P1, ordinary P2, wrong/stale candidate, infrastructure failure, exhausted allowance, disabled rung, pin, unavailable model, provider constraint, profile change, and persisted selected/effective provenance. Use a fake runtime to verify that reservation, spawned agent, retained run and Frontier activity agree on one policy. Include a bounded automatic repair-loop test so an upshift cannot create another attempt.
4. **Run short, frozen Repair replays.** Prepare two independently checked, real candidate defects from development cases, each with the broken candidate SHA, authorizing gate, upstream artifacts and unchanged tool/prompt limits. Confirm before dispatch that the unchanged candidate fails the checker and the known reference passes; stop if either case cannot be qualified. Exclude the reference patch and later history from the agent workspace. Replay only the Repair role from that state in fresh isolated worktrees. Compare selected versus proposed stronger policy with two repetitions per case (eight calls for one provider pair); keep provider pairs separate. Grade the resulting candidate with the independent behavior checks and a material-defect review. Record repair success, regressions, elapsed time, tokens and API-rate estimate per attempt. Routing controls use no model calls. H03 stays held out.
5. **Promote narrowly.** First screen Sol High against Sol XHigh for standard/high-risk Codex Repair; Astra is a later challenger if that pair does not justify an upshift. Run a separate Sonnet High versus Opus High replay before claiming the all-Claude rung improves outcomes. A small replay can reject an obviously poor rung but cannot establish a population success rate. Enable a new default only if the stronger policy fixes more independently graded defects without material regressions and the incremental cost is justified; otherwise leave the rung Off or operator-selected. Finish with a fixture-backed orchestration smoke test of candidate revision and fresh-gate invalidation; a full paid workflow is not required to qualify this slice.

## Acceptance and handoff

- Same input and task snapshot always yield the same policy decision. No attempt is duplicated; limits and human controls remain intact.
- The Frontier run record shows selected model/effort, actual model/effort, trigger and authorizing candidate gate. Evaluation exports count policy divergence and all replay attempts, including failures.
- Focused tests, typecheck, lint, and the applicable Frontier checks pass. The diff contains no provider change, workflow-depth change or H03 result.
- Deliver the implementation as a separate PR from #129 with the frozen replay manifest, per-case results and a promote/retain recommendation. Package-attempt escalation can follow once per-attempt reservation/provenance is designed and tested; Plan/Specification uncertainty routing remains a separate task.
